# CI Hardening & SLSA Level 2+ Strategy

## The Problem
Currently, our release process (`release-talos-assets.yml`) re-builds all artifacts at the moment a Git tag is applied. This approach leads to several major anti-patterns:
1. **Slow Releases:** Applying a tag takes 15-30+ minutes because the entire world is rebuilt.
2. **Hidden Failures:** Broken patches or misconfigurations are often only discovered *during* the release tag phase, halting deployments when we need them to be fastest.
3. **Cache Invalidation & Redundancy:** We recompile artifacts that the `main` branch already compiled, risking inconsistent environments and overwriting previously valid cache layers.
4. **Vibes-Based Tagging:** Because the tag workflow is so heavy, we often tag a commit without waiting for the `main` CI to prove the commit is actually buildable.

## The Goal (SLSA Level 2 / 3 Alignment)
We must evolve the CI/CD pipeline so that **Release Tags NEVER build code.** A release tag should solely promote pre-existing, verified artifacts. 

This aligns closely with DevOps agility principles and SLSA (Supply Chain Levels for Software Artifacts) Level 2 & 3:
*   **Shift Left (Fast Feedback):** Failures that could break a tag should be exposed in the PR CI (branch builds). Failures that could break `main` should be fully tested in `main` CI.
*   **Immutable Provenance:** When `main` CI passes, it should output a provenance manifest (e.g., writing the specific `sha256` image digests to a `LATEST_BUILD.md` file).
*   **O(1) Tagging:** The `release-talos-assets.yml` workflow should simply read the `sha256` hashes from `LATEST_BUILD.md` and use fast network operations (like `skopeo copy` or `crane copy`) to re-tag those exact immutable blobs with the release tag (e.g., `v1.4.0-1.13.2`).

## Execution Plan & Balance

To implement this without exploding the complexity of our CI workflows, we will adopt a tiered validation approach:

### 1. PR / Branch CI (Lean & Fast)
*   **Goal:** Provide fast feedback to developers.
*   **Action:** Only execute the most fragile or modified components. For us, this means validating the Talos Imager patches (e.g., applying `01` through `10` patches and running a dry-build or lint). We skip building standard Cozystack packages unless their source files changed, as they are highly reliable.

### 2. Main Branch CI (The Canary Builder)
*   **Goal:** Seed the registry cache and produce candidate artifacts.
*   **Action:** When a PR merges, `main` CI builds the entire suite (all 31+ OCI images and flashable metal images).
*   **Artifacts:** These are tagged with a transient label (e.g., `canary` or `main-<commit-hash>`).
*   **Provenance:** The final step of `main` CI is generating a manifest of the immutable `sha256` sums for all produced artifacts.

### 3. Release Tag CI (The Promoter)
*   **Goal:** Instant, mathematically guaranteed releases.
*   **Action:** When a semantic version tag (e.g., `v1.4.0-1.13.2`) is pushed, the CI workflow triggers. It skips the `make` build entirely. Instead, it reads the provenance manifest generated by the `main` CI and uses `skopeo` or Docker Buildx to promote those exact `sha256` layers to the new release tag.
*   **Result:** Releases take 30 seconds instead of 30 minutes, and we guarantee that what we release is exactly what `main` tested.

By shifting the heavy lifting to the `main` branch and treating tags strictly as pointers, we establish a robust, professional "System for Success."
